# SQLite → Postgres — migration evaluation

> **Status: evaluated, not adopted (2026-06-25).** SQLite is retained. This records
> *what the migration would involve, what it would and wouldn't buy us, and the
> triggers that would make it worth doing* — so a future session doesn't re-derive it.
>
> Related: PLAN.md §9 risk row "SQLite write concurrency"; the SQLite gotchas in this
> repo's `CLAUDE.md`; the generated `docs/schema.sql`.

## TL;DR

For a **single-household, single-Pi, read-heavy, low-write-concurrency** app, **SQLite
is a defensible permanent choice.** Every SQLite workaround we've hit (the `member_id`
bare-FK in migration `015`, `render_as_batch`, the `PRAGMA` setup) is a *migration-authoring
annoyance*, not a *runtime problem*. We are nowhere near SQLite's real limits.

- **Would Postgres be faster? No** — same or *slightly slower* on a Pi (see below).
- **Is it worth migrating?** Only for **correctness/ergonomics** (real `timestamptz`,
  native FK enforcement, no batch-rebuild migrations), not for performance or scale.
- **Effort:** ≈ **1.5–2 focused days**, with the live-DB data load being the only
  genuinely risky step.

## Would it make the app faster?

**No.** The engine is not the bottleneck at this scale, and on a Pi Postgres can be a
net negative:

- **SQLite runs in-process** — a query is a function call against a memory-mapped file
  (zero network, zero IPC). Postgres is a separate server process, so *every* query
  crosses a socket. For the simple point/range queries that are ~all of this app,
  SQLite is typically **faster**.
- **WAL is already on** (`app/core/database.py`) → concurrent readers + one writer.
- **On a Pi**, Postgres is a persistent process (~30–50 MB+ idle) taking RAM *away*
  from the page cache SQLite relies on.

Postgres only wins on speed under conditions we don't have: high concurrent-write
contention (SQLite serializes writers — we have ~none), datasets that exceed page cache,
or complex analytical/parallel queries.

**If something feels slow, look here instead** (all DB-engine-independent):
1. **Recurrence expansion** — `get_occurrences` / `get_task_occurrences` expand RRULEs
   in Python (`app/services/tasks.py`, `app/services/calendar.py`). CPU-bound; Postgres
   wouldn't touch it.
2. **N+1 queries** — eager-load relationships (`selectinload`) in hot read paths.
3. **Network round-trips** — DDNS hop → Next.js `/api/backend/[...path]` proxy → Caddy
   → Clerk JWKS often dominate perceived latency.

Index coverage is already good: `family_id` is indexed on every table and all FKs are
indexed, so the usual "missing index" cause doesn't apply.

## How little is actually coupled to SQLite

The query layer is **already effectively dialect-agnostic.** The only SQLite-specific
code is **one file**:

- **`app/core/database.py`** — `check_same_thread`, `StaticPool` (in-memory tests), and
  the `PRAGMA foreign_keys=ON` / `journal_mode=WAL` connect listener. **All already gated
  behind `if _is_sqlite`,** so Postgres simply skips them.

Everything else (`func.count`, `func.coalesce`, `func.sum`, `func.now()`) is portable
SQLAlchemy. The only raw SQL in the app is those two PRAGMAs.

## What the migration involves

### 1. Engine + deps (trivial, ~1h)
- Add `asyncpg` to `pyproject.toml`. (Works for **both** the app engine *and* Alembic's
  async `env.py` — no `psycopg2` needed.)
- `DATABASE_URL` → `postgresql+asyncpg://USER:PASS@postgres:5432/skylight`. The existing
  `_is_sqlite` branch no-ops the SQLite-only setup automatically.

### 2. The migration chain — the real work (~half day)

Replaying the 15 existing migrations on Postgres is the landmine field; they were
autogenerated/tested against SQLite:

- **`012_remove_calendar_entity.py:57`** — `UPDATE ... SET synced = 1`. Integer `1` into
  a boolean column. **Postgres rejects integer→boolean** (wants `true`). Hard break.
- **`render_as_batch=True`** (`alembic/env.py`) is the SQLite ALTER workaround; on PG it
  still runs but does pointless full-table-copy rebuilds. Make it conditional on SQLite.
- **Native enums** — on SQLite `Enum(...)` is VARCHAR+CHECK; on PG it's `CREATE TYPE …
  AS ENUM`. Replaying create/add-column across migrations risks **double-creating** the
  same named type.

**Recommended path: don't replay the SQLite chain.** We control the one DB, so squash to
a **fresh Postgres baseline** — generate one new initial migration from `Base.metadata`
against an empty Postgres, `alembic stamp` it, and keep the old chain only as history for
the legacy SQLite file. Cleaner than retrofitting 15 migrations to be PG-safe.

### 3. Add a naming convention (do it with the baseline)

`Base.metadata` has **no** `naming_convention`. SQLite is lax; on Postgres, stable
constraint names matter for future autogenerate/drops (e.g. the unnamed
`UniqueConstraint("user_id","family_id")` on `memberships`). Add a
`MetaData(naming_convention=...)` to `app/models/base.py::Base` as part of the baseline.

### 4. Type/behavior changes — mostly upgrades, not problems

| Type in models | SQLite today | Postgres |
|---|---|---|
| `Mapped[uuid.UUID]` (`sa.Uuid`) | CHAR(32) hex string | native `uuid` (indexable) |
| `DateTime(timezone=True)` | **tz silently ignored** (naive string) | real `timestamptz` ✅ correctness win |
| `Enum(...)` | VARCHAR + CHECK | native enum type |
| `Boolean` | 0/1 integer | native `bool` |
| `JSON` (`meal.tags`), `Text` (weather blob) | TEXT | native `json` (could upgrade to `JSONB`) |

The `member_id` FK workaround in migration `015` **disappears** — on PG you just write
`ADD COLUMN member_id ... REFERENCES members(id)`.

### 5. Ops / deploy on the Pi (the heaviest part, ~half day)
- Add a `postgres:16` service to `docker-compose.yml` (parent `HomeServerAPI` repo) with
  its own named volume + healthcheck; add `depends_on: {postgres: {condition:
  service_healthy}}` to `skylight-api`.
- **Backups change**: today a backup = copy the `skylight_data` `.db` file. With PG you
  need a `pg_dump` cron. New moving part.
- **Resource cost**: a persistent server process vs. SQLite's zero-process embedded file
  — a real, if modest, tax on a Pi.
- The container entrypoint (`alembic upgrade head` before uvicorn) is unchanged.

### 6. Data migration (risk lives here)
Existing prod rows on the Pi must move SQLite→Postgres. Options: **`pgloader`** (best for
sqlite→pg), a one-off script, or — if the live DB is still basically empty/test data —
**just start fresh**. *Decide this by checking how much real data is in the live Pi DB.*
Note: the deploy's rollback reverts **code, not the DB**, so a botched data load is not
auto-recoverable — snapshot the SQLite file first.

### 7. Tests
Keep the in-memory SQLite harness for speed (`tests/conftest.py` builds from
`Base.metadata.create_all`). Optionally add a Postgres integration run via testcontainers.
Bonus: on PG the test-vs-prod schema divergence noted in `CLAUDE.md` (the `015` FK) goes
away, because the real FK exists in both.

## Effort summary

| Step | Estimate |
|---|---|
| App/engine/deps | ~1 hour |
| Baseline migration + naming convention | ~half day |
| docker-compose + backups + data load | ~half day |
| Verify tests + staged deploy | ~half day |
| **Total** | **≈ 1.5–2 focused days** |

## Decision & when to revisit

**Stay on SQLite** until one of these triggers fires:

- **Write concurrency** actually causes `database is locked` errors under real multi-device
  use (WAL + busy-timeout should prevent this at household scale).
- The app grows **beyond one household / one Pi** (multi-tenant SaaS, horizontal scaling,
  a managed DB) — at which point Postgres is the obvious choice.
- We need a **Postgres-only feature** (JSONB indexing, full-text search, partial indexes,
  `LISTEN/NOTIFY`).
- The **migration-authoring friction** (batch rebuilds, FK-ALTER workarounds) becomes a
  recurring tax worth paying down once.

If/when we do migrate, do it for correctness and ergonomics — and don't expect it to be
faster.
